# AI-First 团队协作 Harness 使用手册

> 面向 5 人前后端团队的 AI 开发协作流程操作手册。基座 = AI-First Coding Loop(AIFCL);
> 本手册覆盖本仓 `feat/ai-collab-harness` 分支落地的全部功能。
> 设计依据见 [docs/superpowers/specs/](superpowers/specs/),逐步实现计划见 [docs/superpowers/plans/](superpowers/plans/)。

---

## 0. 一句话定位

把"需求 → 任务拆解 → AI 辅助开发(强制规范)→ 自动评审 → 架构师(CTO)评审 → 合并部署 → 自动生成测试任务 → QA 执行 → 测试 agent 审核 → 回测"整条链路工程化,
**规范的最终保证来自机器门禁(CI + 评审 gate),不靠 agent 自觉;凡产生外部副作用的动作都要人确认。**

> ⚠️ **架构边界(重要,2026-06 更新)**:本 harness 聚焦**客户端执行侧**(规范 skill + 四趟 AI 评审 + 特性开关 + 自愈环)。**任务拆解、任务派发、进度、issue 中心(单一事实源)、测试验证网关由管理端 deepdog-BIOS 负责**,harness 已**移除**对应实现(`task_splitter`/`create_issues_from_draft`/`team-ops`/`gen_test_tasks`/`qa_review`/`qa-handoff`)。下文 §3 流程中"任务拆解 / 测试任务生成 / QA 审核"由 deepdog 承担,harness 只提供 CI 侧四趟评审信号(经 `check_suite` webhook 回流 deepdog)。被抽存供 deepdog 复用的 prompt 见 [docs/assets-for-deepdog/](assets-for-deepdog/);职责边界权威说明见 spec §2.5。

## 1. 安装与初始化

### 1.1 把 harness 装到你的项目仓
```bash
# 在本脚手架仓根目录执行,把 core/ + claude-code/ 装到目标代码仓
bash tools/install.sh <你的项目仓目录>

# 选项:
#   --codex            装到 .codex/ 而非 .claude/
#   --no-skills        只装 core/,不装 skills/agents
#   --strategy 1|2|3   合并策略(默认 2:保留你已有 README/Makefile/Dockerfile)
```
安装会:分发 core 脚本/workflow/prompt、claude-code 的 skills/agents、`CLAUDE.md`(仅当目标无该文件)、
`.claude/settings.json`(含 skill 提醒 hook)、5+1 个 Issue Form 到 `.github/ISSUE_TEMPLATE/`,
并在末尾调用 `ensure_skills.sh` 校验 skill 就位。

### 1.2 确保 skill 就位(幂等,可重复跑)
```bash
bash tools/ensure_skills.sh <你的项目仓目录>
```
- 团队规范 skill 随仓下发(已在 `.claude/skills/`),脚本只校验存在性。
- superpowers:用户级/项目级 × skills/plugins 四路径任一存在即视为已装;缺失则提示。
  **确切安装命令以官方为准**(可用 claude-code-guide 核实当前 plugin marketplace 命令)。

### 1.3 必须手工完成的初始化
1. 编辑根 `CLAUDE.md`,把 `[占位]` 换成项目真实信息(目录结构、`make test-integration` 等命令、安全禁区)。
2. GitHub 仓库 Settings:
   - Variables:`LLM_PROVIDER`(anthropic/openai/...);可选 `LLM_BASE_URL`、`LLM_MODEL_VERIFIER_*` 分趟模型覆盖
   - Secrets:`LLM_API_KEY`
3. Branch protection(关键!)把 `ci-gate` 与 `ai-review-gate` 设为 **required check**,勾选 **Do not allow bypassing**。
4. 多仓共享文档:各代码仓用 git submodule 引入 `docs-repo`(`docs/` 指向它);跨端契约放 `docs-repo/contracts/`。
5. 管理仓:用 `templates/team-ops/` 初始化一个 `team-ops` 仓(每日计划、ownership、Projects 配置)。
6. 组织级 GitHub Projects:建一个跨多仓聚合的看板,所有 issue 进同一视图。

## 2. 角色与职责

| 角色 | 用什么 | 干什么 |
|---|---|---|
| CTO / PM | `architect-task-writer` + `task-splitter` skill | 写任务规约、每日拆解、确认草稿、人工评审 PR |
| 前端/后端同事 | `implementer`(写码自带测试+文档)+ `checker`(自检) | 领 issue、按规范开发、本地自检、提 PR |
| CTO(评审) | 四趟 verifier + 人工 review task | 评审 PR、批准合并 |
| 测试同事 | `qa-generator`/`qa-reviewer` agent | 领 qa-task、执行测试、提交报告 |

项目级/子服务级责任归属:用 `CODEOWNERS` + `team-ops/ownership.md` 固化(相对静态)。

## 3. 每日工作流(端到端)

> 🔧 **本节部分环节已移交 deepdog**(见 §0 架构边界):§3.1 任务拆解、§3.4–3.6 测试任务生成/QA 审核所引用的 `task_splitter`/`gen_test_tasks`/`qa_review` 等命令**已从 harness 移除**,改由管理端 deepdog 承担。harness 侧实际保留的是:同事按规范开发(§3.2)→ 提 PR → **CI 四趟评审**(§3.3)→ PR 信号经 webhook 回流 deepdog。下方相关小节保留作流程示意,命令以 §4 为准。

### 3.1 CTO:每日任务拆解(三层模型第③层)
```bash
# 1) 拆解 → 只产出"计划文档 + 待建 issue 草稿",绝不建 issue(人工确认门第一道)
python3 scripts/task_splitter.py \
  --source <当日任务源.md> \
  --date $(date +%F) \
  --plan-out team-ops/daily/$(date +%F).md \
  --draft-out state/tasks/draft-$(date +%F).json

# 2) 人 review 草稿 JSON:核对每条 repo(代码仓)、assignee、daily-task 六字段、验收可测

# 3) 确认后建单(人工确认门第二道:需 --confirm;默认 dry-run 不真建)
python3 scripts/create_issues_from_draft.py --draft state/tasks/draft-$(date +%F).json --confirm   # 先 dry-run 预览
TRACKER=github-cli python3 scripts/create_issues_from_draft.py --draft state/tasks/draft-$(date +%F).json --confirm  # 真建(需 gh auth login)
```
> issue 建在各自的**代码仓**(不是管理仓),这样 PR `Closes #N` 才能自动关单。

### 3.2 同事:领 issue → 开发
- agent 进项目先读 `CLAUDE.md`;按改动内容自动/强制加载规范 skill(见 §5)。
- 强制:自带测试、改接口同步更新 `docs/api`、改数据模型同步 `docs/data-model`、新功能藏特性开关后。
- 本地自检(checker)通过 → 提 PR,PR 描述里写灰度计划与需人重点看的战略风险。

### 3.3 PR:四趟自动评审 + CTO 人工评审
- 开 PR 自动触发四趟评审(见 §6)+ CI 门禁;任一 BLOCK → 合不进。
- 自动建一个 `review` 类型 issue 指派 CTO;CTO 按标准评审 → 批准。
- 两个 gate 全绿 + CTO 批准 → 合并 `main`。

### 3.4 合并后:自动部署 + 测试任务生成
- 合并触发六阶段部署(`deploy.yml`)。
- 同时 `qa-handoff.yml` 触发 `gen_test_tasks.py`:读本次合并 diff → 生成测试用例/流程/验收 → 建 `qa-task` issue → 记账 `state/qa-history.jsonl`。

### 3.5 测试同事:领 qa-task → 执行 → 提交报告
- 在组织级 Projects 领取 `qa-task`,按 issue 内测试用例执行。
- 按 `qa-report` 模板提交测试报告(评论形式,含覆盖验收点 + 证据)。

### 3.6 测试 agent:审核报告 + 回测
- 报告评论触发 `qa_review.py`:核对是否覆盖全部验收点 + 是否有证据 → `VERDICT: PASS|BLOCK`。
- **保守默认:缺判定或歧义 → BLOCK**(测试审核不误放行)。
- PASS → 关单 + 记账;BLOCK → 留言打回(回测),必要时重开 dev 任务。

## 4. 命令速查

| 命令 | 作用 | 安全默认 |
|---|---|---|
| `tools/install.sh <repo>` | 安装 harness 到目标仓 | 幂等,改过的文件跳过不覆盖 |
| `tools/ensure_skills.sh <repo>` | 校验/提示 skill 就位 | 已存在则跳过 |
| `scripts/ai_review.py --pass {quality\|security\|performance\|dependency} [--mock]` | 单趟 AI 评审 | --mock 不调真实 LLM |

> 本地从 `core/scripts` 跑评审脚本时,prompt 路径设 `AIFCL_PROMPTS_DIR=../prompts`;CI 里以仓根为 cwd 无需设置。
>
> 🗑 **已移除的命令**(移交 deepdog 管理端,见 §0 架构边界):`task_splitter.py`、`create_issues_from_draft.py`(任务拆解→deepdog issue/派发);`gen_test_tasks.py`、`qa_review.py`(测试闭环→deepdog verification 网关)。

## 5. 规范 skill 体系(11 个判断层 + 三层加载)

### 5.1 何时加载哪个
| 改动涉及 | 加载 skill |
|---|---|
| SQL/ORM/迁移 | `sql-optimization` |
| 外部调用/并发/缓存/日志/监控 | `performance-review` |
| 用户输入/鉴权/密钥/序列化 | `secure-coding` |
| 金额/价格/余额/交易 | `financial-numerics` |
| 改接口 / 改数据模型 | `api-doc-output` / `data-model-output` |
| 任何改动底线 | `clean-code` + `testing-standards` + 新功能 `feature-flag-setup` |
| 其余 | `naming-convention`、`commenting`、`design-patterns` 按需 |

### 5.2 三层加载机制(都生效)
1. **自动触发**:每个 `SKILL.md` 的 `description`/`when_to_use` 让 agent 自行加载。
2. **强制挂载**:`agents/implementer.toml` 的 `required_skills`(底线)+ `optional_skills`。
3. **主动提醒**:`.claude/settings.json` 的 UserPromptSubmit hook 按改动类型提示。
> 机器能判定的(格式/命名大小写/覆盖率/SAST)交 linter/CI;skill 只承载需判断的部分。

## 6. 四趟 AI 评审

| 趟 | 覆盖问题库类 | 模型档建议 |
|---|---|---|
| quality | 1 正确性 · 9 可维护 · 10 测试 · 12 文档 | 标准 |
| security | 6 安全 | 旗舰(别省) |
| performance | 2 并发 · 3 DB · 4 韧性 · 5 性能 · 7 可观测 | 标准 |
| dependency | 13 依赖 | 便宜 |

- 完整 13 类清单见 `prompts/issue-checklist.md`;团队痛点(无超时/重试/幂等/限流、日志不结构化、缺埋点、SQL 全表/N+1)标 **BLOCK 级**。
- 切厂商只改 `LLM_PROVIDER` + `LLM_API_KEY`;可用 `LLM_MODEL_VERIFIER_<ROLE>` 分趟覆盖模型。
- 四趟并行,`ai-review-gate` 汇总:任一趟 BLOCK → gate 红。

## 7. Issue 类型与模板

| type label | 用途 | 谁建 | 关闭条件 |
|---|---|---|---|
| `daily-task` | 每日任务 | task_splitter(人确认后) | 关联 PR 合并 + 测试通过 |
| `feature` | 功能开发 | 拆解产出 | PR `Closes` |
| `bug` | 缺陷修复 | 人/自愈环 triage | 修复 PR 合并 |
| `qa-task` | 测试任务 | gen_test_tasks(合并后) | qa_review 审核 PASS |
| `review` | CTO 评审任务 | PR 打开时自动建 | CTO 批准 |
| `qa-report`(模板) | 测试报告格式 | 测试同事填 | — |

模板源在 `templates/team-ops/issue-templates/`,install 时分发到代码仓 `.github/ISSUE_TEMPLATE/`。

## 8. 门禁与人工确认门

### 8.1 机器门禁(GitHub 分支保护必配)
- required check:`ci-gate`(lint/类型/SAST/覆盖率/契约/bundle)+ `ai-review-gate`(四趟)
- 勾选"禁止绕过"——连管理员也绕不过。

### 8.2 人工确认门(凡外部副作用,人点才执行)
- 建 issue:task_splitter 只产草稿 → 人 review → `create_issues_from_draft --confirm` 才建。
- 合并:门禁是机器否决权,放行由 CTO 点。
- 部署/关单:同理。

---

## 9. 防失控(基座能力,建议开启)
- `daily-health.yml`:每日健康报告 = token 账单(月预算外推 + 80% 告警)+ **反认知投降三指标**(comprehension-coverage / pr-read-rate / agent-modification-rate),低于阈值红线告警。
- 自愈环 `triage.yml`:线上错误聚类 → 九维打分 → 建单 → 修复后 `verify_triage` 复检关单。
- 特性开关:新功能藏开关后,支持灰度与 kill switch。
